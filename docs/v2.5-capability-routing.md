# v2.5 能力路由设计（工作大类 · 可选探测 · ETA 选机）

> 状态：v2.5.0 已实现三项视频探测；其余类别待 v2.5.1。基线 v2.4.3。
> 一句话：把「哪台机器更强」换成「这个任务、这台机器现在跑，预计多久跑完」，并且让用户自己跑一次探测就知道边界。

## 1. 三条原则

1. **能力是「机器 × 工作大类」的矩阵**，不是单机总分。
   GT14 转码 156–182 fps，补帧只有 14.4 fps，两项差一个数量级；不能用一个 `score` 概括。
2. **探测是用户动作，不是定时任务。**
   跑一次要几十秒到几分钟，默认不自动跑；用户点「能力探测」，可勾选类别。v2.5.0 不提供取消（本机同步执行，关窗不中断），取消放 v2.5.1。超过 30 天未测只提示「已过期」，不自动重测。
3. **未测不阻塞，但不能装作知道。**
   v2.5.0 没有实测时**回退最闲机器**，不伪造先验值，也不在回执里写 `routeReason/confidence`（这两项放 v2.5.1）。用户可为高风险任务打开「只许实测机器」（v2.5.1 接线）。

## 2. 工作大类目录（首版 8 类）

| id | 用户看到的名称 | 统一指标 | 探测样本 | 预计耗时 |
|---|---|---|---|---|
| `video.transcode` | 视频转码 / 压制 | 帧/秒（1080p H.264） | 10 秒 1080p 片转 H.264 | 10–20s |
| `video.interp` | 视频补帧 | 帧/秒（1080p 30→48） | 2 秒片补到 48fps | 约 45–60s（单流 + 2–6 路并发采样，wall） |
| `video.render` | 合成 / 渲染 | 帧/秒（1080p 无头浏览器） | 240 帧 canvas 渲染 | 20–60s |
| `image.generate` | 图像生成 | 秒/张（512×512） | 连续 2 张 | 20–120s |
| `audio.tts` | 语音合成 | 字符/秒（或 ×实时） | 200 字合成 | 5–20s |
| `llm.text` | 文本 / 代码对话 | token/秒（输入 512） | 生成 256 token | 10–40s |
| `llm.vision` | 视觉理解 | 图/分钟 | 3 张图描述 | 15–60s |
| `io.copy` | 数据搬运 / 磁盘 | MB/秒 | 512MB 顺序写 | 5–20s |

> 类别名可以改，id 不改（任务里存 id）。用户勾选「这台机器主要做哪些工作」只影响 UI 默认展示与探测推荐，不硬性禁止别的任务。

## 3. caps 2.1 数据结构

```jsonc
{
  "schema": 2.1,
  "identity": { "machine": "GT14", "os": "Windows 11", "cpu": "...", "cores": 10, "memGB": 32 },
  "gpu": [{ "name": "RTX 4070", "vramGB": 12 }],
  "tools": { "ffmpeg": { "path": "...", "version": "N-126492", "hw": ["nvenc","qsv"] } },
  "workloads": [
    {
      "id": "video.interp",
      "unit": "fps",
      "value": 14.4,
      "samples": 3,
      "confidence": "measured",          // measured | inferred | declared
      "workload": { "width": 1920, "height": 1080, "fpsIn": 30, "fpsOut": 48 },
      "measuredAt": "2026-11-14T10:00:00Z",
      "benchVersion": 1
    }
  ],
  "limits": { "maxConcurrent": 2, "quietHours": [0, 7], "allowUnverifiedHighRisk": false }
}
```

- 同一 `id` 只保留一条；重测覆盖，旧值进 `history`（最近 10 次，供趋势图，v2.5.1）。
- `confidence` 只由数据来源决定：探测脚本写入 `measured`，人工填写 `declared`，由名称/规格推断 `inferred`（或 `low`）。
- 不用探测结果做鉴权/准入，只用于排序与 ETA。

## 4. 探测流程（面板）

```
机器卡 →「能力探测」
  1. 勾选类别（默认：这台机器已声明的重点类别；全选显示预计总耗时）
  2. 开始 → 任务落到该机器执行（exec 模式，脚本自带进度文件）
  3. 面板显示当前类别与已用时间；v2.5.0 无取消（关窗不中断），取消放 v2.5.1
  4. 完成 → 结果表（各项数值、confidence、与上次对比）
  5. v2.5.0 由探测路由直接写回本机能力卡（旧卡读不到就不写）；“先确认再保存”放 v2.5.1
```

- 探测脚本：`scripts/probe-workload.ps1 -Workload video.interp -Out <json>`，每类一个固定小样本；失败只标记该类 `failed`，不影响其它类。
- v2.5.0 在本机同步跑（`execFile` pwsh），关掉面板不影响；取消与远程执行放 v2.5.1。
- 读不到旧卡时直接 503 不写，避免浅合并覆盖 identity 与其它类。

## 5. 路由（board_dispatch）

输入：`taskKind`（映射到 workload id）、`size`（帧数/字数/图数）、可选 `model`。

1. **准入**：`requires` 硬过滤（已有）。`onlyMeasured`（只允许实测机器）放 v2.5.1。
2. **估时**：`eta = size / value + 8s`；v2.5.0 无实测时回退“最闲”，先验与低置信标注放 v2.5.1。
3. **选择**：在通过准入的机器里取「预计完成时间最早」的一台；并行拆分按 wall-clock 取 max，不按总吞吐。
4. **稳定阈值**（已确认）：
   - 两台 ETA 差 ≤ 15% → 不换机，避免抖动；
   - 单任务**计算时间** < 2s（不含 8s 固定开销）→ 不跨机，保持 ETA 最短的机器。
5. **回执**：v2.5.0 只在 `board_dispatch` 的回执里带 `workload/size/etaSeconds`（建单 payload 未变）；任务字段与 `routeReason/confidence` 放 v2.5.1，历史回写放 v2.5.2。

## 6. 与「模型选择」的关系

- `llm.text` / `llm.vision` 的 workload 是「机器级」吞吐；具体模型仍由 `model` 字段选择（v2.1.0 已有）。
- 模型清单里的 `tags` 负责「哪类任务适合」，workload 负责「这台机器跑这类任务多快」；两者不混。
- 用户打开「允许未验证模型承担高风险」时，路由仍按实测 ETA 排序，但回执标 `policy: user-override`。

## 8. 非目标

- 不做跨机迁移中的任务（task 一旦 claimed 不换机）。
- 不做「自动定时基准」；不做跨网络吞吐探测（Z: 网络盘单列，不混进本机 io）。
- 不把探测结果当安全边界；高风险开关仍是显式用户选择。

## 9. 已确认（2026-11-14）

1. 8 类目录按此命名，id 固定。
2. 首版只做视频 3 类探测（安全考虑，先跑通再扩）。
3. 入口用独立「能力探测」，与机器卡的能力卡配置分开；首版只测本机。

## 10. 稳定性与压测证据（v2.5.3）

来源：PC2 自答里有一条「30 天内没有任何显卡 TDR（掉驱动）事件」（`Get-WinEvent System` / provider `Display`）。这条值得进能力卡，但它只说明「过去没崩过」，不说明「满载能扛住」——很多机器从没被这样压过。

### 10.1 两个维度，分开记

- **历史稳定性**：过去 30 天系统事件里的异常计数（只读、只存聚合数，不存事件正文）。
- **压测证据**：这台机器在我们手里真正跑过重活的记录；没有记录时明确标「未压测」，不用历史稳定冒充。

### 10.2 历史稳定性探测（约 2–3 秒，只读）

读取 30 天（另给 7 天窗口用于判级）：
- `Kernel-Power` 41（非正常断电/重启）、`BugCheck` 1001（蓝屏）、`EventLog` 6008（意外关机）；
- `WHEA-Logger` 17/18/19/47（硬件纠错/致命）；
- `Display` 4101（TDR 掉驱动）、`nvlddmkm` 13/14/153；
- `Disk` 7/11/51、`Ntfs` 55（磁盘/文件系统错误）；
- `Application Error` 1000、`Service Control Manager` 7031/7034（服务崩溃）；
- 额外：`Kernel-Processor-Power` 37（降频/热限制）、当前 uptime、上次启动时间、挂起重启标志、显卡驱动版本、GPU 温度。

等级（默认保守，可被用户覆盖）：
- `good`：30 天无上述严重项，且 7 天无 TDR/WHEA/蓝屏；
- `watch`：30 天内 1 次 Kernel-Power、或存在意外关机、应用崩溃 >5、服务崩溃 >5；
- `risky`：7 天内 TDR/WHEA/蓝屏任一 >0，或 30 天 Kernel-Power ≥2，或磁盘/文件系统错误 >0；
- `unknown`：事件读取失败（`confidence: inferred`），不伪装成 good。

### 10.3 压测证据

- 记录 `{at, seconds, workload, ok, maxTempC, throttled}`，最近 5 次。
- 首次重活前的「压测」= 60 秒 CPU + NVENC 1080p 编码（可取消）；跑完把温度/是否降频/是否成功写回。
- 失败或中途异常 → 直接标 `risky`，且不再自动派重活。

### 10.4 能力卡 schema 增补

```json
"stability": {
  "windowDays": 30,
  "events": {"kernelPower": 0, "bugcheck": 0, "whea": 0, "tdr": 0, "disk": 0, "appCrash": 0},
  "lastEventAt": null,
  "uptimeHours": 52.4,
  "pendingReboot": false,
  "level": "good|watch|risky",
  "confidence": "measured|inferred",
  "evidence": {"heavyRuns": 1, "lastHeavyAt": "2026-11-14T12:00:00Z", "lastBurnIn": {"at": "...", "ok": true, "maxTempC": 71}}
}
```

### 10.5 重活派工门

- 「重活」定义：预估 >5 分钟，或 GPU 密集（转码/补帧/渲染/图像生成）。
- `risky` → **不自动跨机派重活**，回执要求用户显式确认，并建议先压测；
- `watch` → 允许但回执带 warning；
- `good` 但无压测证据 → 允许，回执标「未压测」，面板给「先跑 60 秒压测」按钮；
- 非重活不受此门限制。

### 10.6 面板

- 能力卡新增一行：「稳定性：30 天 0 次 TDR · 上次压测 2026-11-14 20:30 · 良好」；
- 重活派工前若 `risky` 或未压测，弹一次警告/建议压测，不重复骚扰。

### 10.7 压测时长与维度（2026-11-14 调研）

公开资料的口径基本一致：**60 秒只能算“体检”，不能算“稳定”**。

- FurMark 官方 FAQ：快速评估 15–30 分钟；完整 burn-in / 散热验证 1–2 小时；2 小时无花屏/无降频可认为高度稳定。
- OCCT 指南：CPU 30–60 分钟；内存 ≥60 分钟（抓间歇性错误建议 2 小时+）；初次基线 30 分钟/项；风冷 85–90°C 属可接受上限，持续 >95°C 说明散热不足，>100°C 必降频。
- OpenStack Ironic 的硬件 burn-in：CPU/内存/GPU 默认 24 小时，可配置缩短（文档示例 10 分钟）；内存压 98%、GPU 显存压 95%；测试输出要留档。

对我们的结论：
1. 压测应跑**我们自己的负载**，不是 FurMark 的毛皮渲染：1080p NVENC 编码 + 多路补帧（CPU+内存带宽）；首版不跑磁盘写。
2. 分三档：
   - **快速体检 3 分钟**：只抓“一压就崩/一压就掉驱动”，用于日常复检；
   - **标准 10 分钟**：首次重活前的默认门槛，能进入热稳态、看得出降频与吞吐衰减；
   - **深度 60 分钟**：用户手动选，验证长时间稳定性（电源/散热隐患）。
3. 判定不只看“有没有崩”，还看：
   - 最高 CPU/GPU 温度、是否触发降频（NVML throttle reasons）；
   - 压测窗口内新增的 WHEA / TDR / Kernel-Power 41；
   - 吞吐漂移：后 1/3 的平均 fps 比前 1/3 低 >20% 视为散热/供电不稳；
   - 帧率变异系数 CV >15% 视为不稳。
4. 60 秒不进入 `level` 判定，只作为“快速体检”记录，避免把没热起来的结果当稳定。

### 10.8 隐私边界（硬约束）

- 只读本机事件日志，**只取计数与时间**；不读取、不保存事件正文、进程名、命令行、文件路径、用户名、SID。
- 不采集序列号、UUID、MAC、主板/硬盘序列号；硬件只留型号名（如 `NVIDIA GeForce RTX 3070 Ti`）。
- 压测必须由用户点击触发，**不后台自动跑**；跑之前展示“将采集什么”。
- 原始事件与 ffmpeg 日志不落盘；能力卡只存聚合计数与最近**一次**压测摘要（v2.5.3）；“清除本机能力数据”与“关掉共享”开关尚未实现。
- 能力卡同步到作业板是产品目的（团队选机），但每台机器可单独关“参与能力卡共享”；关闭后只在本机显示。
- 更新检查只发版本号，不携带任何能力/稳定性数据。

### 10.9 v2.5.3 实现状态（以此为准）

首版与上面设计稿的差异，按实际实现记录：

- 只保存**最近一次**压测摘要 `evidence.lastBurnIn`：`{at(ISO), mode, ok, maxTempC, driftPct, reasons[]}`；“最近 5 次”、`lastEventAt`、`heavyRuns/lastHeavyAt` 尚未实现，留后续版本。
- `level` 与 `probe-stability.ps1` 一致：7 天内 TDR/WHEA/BugCheck 任一 >0、30 天内 Kernel-Power ≥2、disk>0 或 ntfs>0 → `risky`；Kernel-Power=1、unexpectedShutdown>0、appCrash>5、serviceCrash>5 → `watch`；事件读取失败 → `unknown` + `confidence:"inferred"`（不再伪装成 good/measured）。
- 压测档位：quick 180s / standard 600s / deep 3600s；**默认不做**，用户点击才跑，可取消；取消会杀整棵进程树。
- 压测判据：最高温度 ≥95°C、`drift>20%`、`cv>15%`、窗口内新增 WHEA/TDR/Kernel-Power、无有效 fps 样本。当前负载是 1080p NVENC 编码 + 多路补帧，**不含设计稿里的磁盘写维度**。
- `risky`/未压测**不会自动阻止派重活**，只展示；强制门控与“派工前弹一次警告”留后续。
- “每机可关参与能力卡共享”尚未实现；能力卡目前仍随 caps 同步到板子。
- `caps-apply` 对 stability 做合并：事件逐项取最大、`lastBurnIn` 取较新、`readFailed` 取或；面板保存探测快照不会抹掉压测证据。
- 压测结果只有 `result.error` 为空时才写 `lastBurnIn`；无 ffmpeg / 非 NVENC 只算环境失败，不记“未通过”，编码器自动降级。
- NVML 降频判据是 `hw_slowdown / hw_thermal_slowdown / sw_thermal_slowdown` 任一 Active（通用 `.active` 常为 Not Active，不能用）。
