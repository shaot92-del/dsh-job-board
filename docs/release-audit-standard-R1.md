# 发布前全量审计与可用性评估标准（R1，2026-11-20 立）

> 起因：v2.7.0 发版后点「派工」整槽白屏（React #130）。缺陷自 v2.1.0 起就存在，
> 期间经历 8 个版本的发布、三轮盘古复审、23 项渲染冒烟，**全部没抓到**。
> 本文记录漏检的结构性原因，并给出此后每次发版必须执行的标准。

## 一、为什么会漏（结构性原因，不是运气）

1. **审查范围被裁剪成「改动面」**。我给审查员的任务书是「这 18 条 handoff 改得对不对」「只看上一轮 4 条修好没有」。
   审查员在给定框内全部答对，而缺陷在框外 —— 一个从 v2.1.0 就带进来的括号错位。
   ⇒ 收窄范围等于把「历史遗留缺陷」的发现概率压到零，而历史遗留恰恰是线上事故的主要来源。
2. **门禁只覆盖「静态结构」，不覆盖「用户路径」**。`client-render-smoke` 只渲染主面板（`ask=false`），
   并断言源码里出现某些字符串（`RAW.includes(...)`）。它证明的是「代码长得像写过了」，
   不是「点下去不崩」。用户第一次点派工，就是把这条路径第一次渲染。
3. **假 React 不校验**。它接受任意 type、任意 child，于是最危险的一类错误（对象当节点类型）
   在门禁里不可观测。**门禁的宽容度 = 事故的容忍度。**
4. **复审变成「打分」而不是「反证」**。三轮复审都在回答「我改得对不对」，
   没人被要求回答「哪些代码路径从未被执行过」。缺少反证式提问，就会系统性漏掉休眠分支。
5. **数据条件掩盖了缺陷**。崩溃分支前面有 `pool.length === 0 → return null` 的守卫，
   机器没上报模型时永远走不到。这类「靠数据恰好为空而不崩」的分支，只有把数据形态做成矩阵才暴露。
6. **定位成本高导致过早收敛**。宿主 React 是压缩生产版、无 sourcemap，报错只有编号；
   `slot entry crashed in 'main'` 又是宿主捕获后的表象，很容易把注意力引向服务端数据。
   ⇒ 必须先把「错误编号的准确语义」查清（#130 = 节点类型非法；#31 = 对象被当 child），再动手。

## 二、标准：每次发版必须做的四件事

### R1-1 全量审计（不得按改动面裁剪）

- 审计范围 = **整个插件**：`lib/`、`scripts/`、`tools/`、文档与配置。改动清单只用于定位「本次重点」，
  不作为「只审这些」的依据。
- 必答三项（写进报告，缺一不签核）：
  1. 按严重度列出的问题清单（每条给 `文件:行` + 为什么危险 + 证据）；
  2. **反证清单**：哪些分支/路径没有任何测试执行过，最危险的三条是什么；
  3. 与上一版的**行为差异面**（不只是代码 diff，包括「静默消失」「默认值变化」这类行为）。
- 审查员不得被限定条数；「只看 N 条」类任务书只允许用于「修补验证」，且必须在全量审计之后。

### R1-2 可用性 + UI 渲染评估（必须真实点击、必须截图）

渲染矩阵（每条都要走一遍，空/正常/畸形三态）：

| 路径 | 三态 |
|---|---|
| 主面板 | 正常 / 数据为空 / 接口失败 |
| 派工弹窗 | 正常（机器清单非空、模型清单非空）/ 模型清单为空 / 畸形模型数据 |
| 类型选择 | agent / exec / maint（含票据框） |
| maint 预览 | 本地 / 远程早返回 / 服务端 error |
| worker 卡 | enabled=false / running / 失败 |
| 任务行操作 | 正常 / failed / blocked |
| 窄屏 | ≤1240 / ≤1100 / ≤900 |

- 每条路径至少一张截图留证（放 `docs/audit-<version>/`），并记录「点了什么、看到了什么」。
- **不接受只读代码得出的可用性结论**。可用性 = 真点、真看、留证。

### R1-3 负向门禁（每个修过的缺陷都要留一条「能抓回旧版」的用例）

- 修复必须配一条**能对旧版 FAIL、对修复版 PASS** 的用例，并在发布记录里贴命令与输出。
- 本次已落地：`SMOKE_BUNDLE=<path> node scripts/client-render-smoke.mjs`
  - 旧版（`case/lib-client-2.7.0-crash.bak`）实测：`FAIL 3/26`，含
    `Minified React error #130: expected a string … but got: object`；
  - 修复版实测：`PASS 29/29`。
  - 实测命令与关键输出（2026-11-20 23:44）：

    ```
    $env:SMOKE_BUNDLE='…\case\lib-client-2.7.0-crash.bak'; node scripts/client-render-smoke.mjs
    FAIL  派工弹窗渲染不抛错（2.7.0 此处 #130） — Minified React error #130: expected a string
          (for built-in components) or a class/function (for composite components) but got: object
    FAIL  client-render-smoke：3/26 项不通过      exit=1

    $env:SMOKE_BUNDLE=$null; node scripts/client-render-smoke.mjs
    ok    client-render-smoke：29/29 项通过        exit=0
    ```
- 冒烟的假 React 必须**严格校验**：type 只接受 string/function/symbol，child 不接受普通对象。
  不允许「宽容的假宿主」通过门禁。

### R1-4 发布签核表（DoD，全部打勾才发布）

1. 全量审计报告（含反证清单）——无未决 P0/P1；
2. UI 渲染矩阵走查截图（§R1-2 的七条路径）；
3. 负向门禁用例实测输出（旧版 FAIL / 新版 PASS）；
4. `npm run gate` 全绿（check-text / plugcheck / smoke 严格模式 / 全量单测 / pack-check）；
5. 版本三处一致 + 包内容核对（tgz 文件数与字节、`npm view` 校验）；
6. 部署一致性（本机 profile 与服务端实际版本一致）+ 重启提示；
7. 回滚路径写清（上一版 tag、回退命令、npm deprecate 话术）。

## 三、本次事故的即刻处置（已执行）

- 根因修复：补回外层 `h('div', null, …)` 与模型行缺失的 `h(` / 右括号（v2.7.1）。
- 恢复派工选模型：模型区恒渲染（无数据给置灰占位），自动档先交集、再按机器分组追加各机专属模型。
- 兜底：`PanelSafe` 函数包装器注册进 `main` slot；异常写 `window.__dsbCrash`，槽内降级不白屏。
- 归一再防一层：`asText()` 覆盖 error / workerErr / note / why / diffRes 等文本落点（防 #31）。
- 门禁加固：冒烟升严格模式 29 项（含派工弹窗三态用例 + `h(h(...))` 负向用例 + `SMOKE_BUNDLE` 对照）。
- 事故归档：`03-缺陷修复与经验教训.md` 增补整节；外部三份评估（Kimi 复核、盘古复盘、GLM 检查规范）录入资料库原始档。

## 四、对我自己的约束（写入工作纪律）

- 不再给审查员「只审 N 条」的框；全量在前，收敛在后。
- 每次交付前自问：「这条用户路径上一次被真实执行是什么时候？」答不上来就补用例。
- 门禁的假宿主、假 DOM、假网络，一律按**严格模式**写：宁可门禁红，不可线上白。
